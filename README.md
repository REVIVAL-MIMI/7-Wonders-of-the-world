# 7-Wonders-of-the-world
Полноценный веб‑проект «7 чудес света»: архитектура и структура
Обзор проекта
Тема и функциональность: Веб-приложение посвящено «7 чудесам света» – как официальным, так и добавленным пользователями. На главной странице отображается интерактивный 3D-глобус с отметками расположения официальных 7 чудес света (с заданными геокоординатами). При клике на отметку пользователь видит карточку с описанием, интересными фактами и фотографиями данного чуда. Помимо этого, реализована система пользовательских аккаунтов: авторизованные пользователи могут добавлять собственные «чудеса» на карту, указывая координаты, описание и загружая фото. Пользовательский контент проходит модерацию перед публикацией. На карте пользовательские чудеса отображаются отдельно (отличаются визуально) от официальных, с возможностью фильтрации (например, показывать только официальные или только пользовательские) и поиска по названию/местоположению. Стек технологий: Фронтенд реализован на React, бэкенд – на Java Spring Boot, база данных – PostgreSQL с расширением PostGIS для геоданных, хранение изображений – в облачном сервисе Cloudinary. Ниже подробно рассматривается архитектура – компоненты фронтенда и бэкенда, схема базы данных, API эндпоинты, выбор библиотек для 3D-глобуса, система модерации и дополнительные возможности.
Архитектура приложения
Фронтенд (React)
Фронтенд представляет собой одностраничное приложение (SPA) на React. Он отвечает за интерактивный пользовательский интерфейс: отображение 3D-глобуса, маркеров чудес, всплывающих описаний, форм авторизации и ввода данных. React обеспечивает динамическое обновление интерфейса без перезагрузки страницы. Для управления состоянием приложения (например, список чудес, состояние фильтров, авторизация пользователя) целесообразно использовать Redux или контекст React. Для выполнения AJAX-запросов к бэкенду (REST API) используется библиотека Axios​
medium.com
. Основные функции фронтенда:
Отображение 3D-глобуса: На главной странице в компоненте React встроен интерактивный глобус (см. раздел про 3D-глобус ниже). При загрузке приложения фронтенд запрашивает у бэкенда список официальных чудес (их названия и координаты) и наносит метки на глобус.
Интерактивность меток: Каждая метка (маркер) на карте реагирует на действия пользователя. При клике происходит запрос подробной информации о выбранном чуде (если она еще не загружена) и отображается всплывающее окно или боковая панель с названием, описанием, интересными фактами и фотографиями.
Авторизация и личный кабинет: Фронтенд предоставляет страницы/формы для входа (Login) и регистрации новых пользователей. После успешного логина (через API) приложение сохраняет токен аутентификации (например, JWT) и отображает пользовательский интерфейс (например, кнопку добавить чудо, выход из аккаунта и т.д.).
Добавление пользовательского чуда: Для авторизованных пользователей доступна форма добавления нового чуда: выбор точки на карте или ввод координат, название, описание, загрузка фото. Форма отправляет данные на сервер через соответствующий API (POST /user-wonders). Пользователь может видеть статус своей отправленной записи (например, «на модерации» до одобрения).
Фильтрация и поиск: Интерфейс позволяет переключать видимость слоев: отдельно показывать/скрывать официальные чудеса и чудеса, добавленные пользователями. Также реализован поиск по названию – например, текстовое поле, при вводе в которое фронтенд фильтрует текущий список меток или отправляет запрос на бекенд (GET /wonders или /user-wonders с параметром поиска). Возможен и геопоиск – например, найти чудеса в радиусе X км от указанной точки (благодаря гео-возможностям PostGIS на бэкенде).
Дополнительный UX: Фронтенд обеспечивает удобный UX – загрузку индикаторов при запросах, обработку ошибок (например, показать сообщение если не удалось загрузить данные), адаптивный дизайн для разных устройств (глобус может переключаться на 2D-карту или список на мобильных, при необходимости).
Бэкенд (Spring Boot)
Бэкенд реализован с использованием Spring Boot – он предоставляет RESTful API для всех функций приложения. Spring Boot выбран за зрелость экосистемы и удобство создания REST API и подключения к БД. Основные роли бэкенда:
REST API эндпоинты: Обрабатывает запросы от фронтенда (список чудес, авторизация, добавление нового чуда, поиск и т.д.), формирует ответы в формате JSON. Для организации кода используются контроллеры Spring MVC (@RestController), сервисы и репозитории (DAO) по паттерну MVC.
Бизнес-логика и валидация: Бэкенд проверяет корректность входящих данных (например, заполнены ли все поля нового чуда, валидность координат), применяет бизнес-правила (например, одно и то же официальное чудо нельзя добавлять повторно, пользователь не превышает лимиты добавления и т.д.). Здесь же реализуется логика модерации (например, при добавлении пользовательского чуда ему присваивается статус «pending» и уведомляются модераторы).
Доступ к данным: Через Spring Data JPA бэкенд взаимодействует с PostgreSQL. Репозитории (или DAO) выполняют запросы: получить список официальных чудес, найти пользовательские чудеса по критерию, сохранить нового пользователя или новое чудо и т.д. Spring Boot + JPA упрощает эту работу, маппируя таблицы БД на Java-классы сущностей.
Связь с внешними сервисами: Бэкенд интегрируется с Cloudinary для загрузки/удаления изображений. Например, при получении файла изображения от фронта, сервер вызывает Cloudinary API (через Cloudinary Java SDK) для сохранения файла в облаке и получает URL или ID, который сохраняет в БД. Также бэкенд может взаимодействовать с гео-библиотеками (например, функции PostGIS вызываются через SQL или через JPA-расширения для гео-типов).
Безопасность и авторизация: Spring Boot включает Spring Security для управления аутентификацией. Реализуется JWT-базированная авторизация: при входе пользователя /login проверяет учетные данные (например, сравнивая хэш пароля с сохраненным), и при успехе генерирует JWT-токен. Токен передается фронтенду и сохраняется (в cookie HttpOnly или localStorage). Все защищенные эндпоинты требуют присутствия валидного JWT (проверяется фильтром Spring Security). Также внедряется ролевая модель доступа: у пользователей есть роль (обычный пользователь, модератор, администратор). На уровне контроллеров/методов можно ограничить доступ по ролям, например, только ADMIN может вызывать эндпоинт одобрения чудес. Spring Security позволяет реализовать RBAC (Role-Based Access Control), соблюдая принцип минимальных привилегий​

.

База данных (PostgreSQL + PostGIS)
В качестве базы данных выбрана PostgreSQL, реляционная СУБД, дополненная расширением PostGIS для работы с географическими данными. PostgreSQL надежно хранит структурированные данные приложения​
medium.com
 – списки чудес, пользователей, лайки и пр., а PostGIS добавляет поддержку гео-типов и гео-запросов. Структура хранения координат: Местоположение каждого чуда (как официального, так и пользовательского) хранится в поле типа Geometry(Point) с проекцией WGS84 (широта/долгота). Это позволяет сохранять координаты в одном поле и выполнять пространственные запросы. PostGIS предоставляет ~1300 гео-функций для анализа данных, например расчет расстояния между точками (ST_Distance), поиск точек в заданном радиусе (ST_DWithin), и использует эффективный пространственный индекс для быстрого поиска по географии​
stackoverflow.com
. Благодаря этому можно реализовать функциональность вроде «найти чудеса вокруг меня» или фильтр по близости. Связи и ограничения: В БД спроектированы связи между таблицами через первичные и внешние ключи. Например, таблица с пользовательскими чудесами ссылается на таблицу пользователей (чтобы знать, кто автор). Включены ограничения целостности (нельзя удалить пользователя, не удалив его чудеса, и т.д.) и уникальные индексы (например, уникальный логин/email пользователя). Для оптимизации частоиспользуемых запросов добавляются индексы (включая GIST-индекс для геоданных). Масштабируемость: Если количество данных вырастет (например, очень много пользовательских точек), PostgreSQL позволяет масштабироваться – можно настроить шардирование или партиционирование таблиц по географическому признаку или по дате добавления, использовать реплики для разгрузки чтения и т.д.​
medium.com
. Однако в рамках данного проекта объем данных относительно небольшой, поэтому стандартной настройки достаточно.
Хранение медиа (Cloudinary)
Изображения и другие медиа-файлы (например, фотографии чудес, в том числе 360°) хранятся вне самой базы данных – в облачном сервисе Cloudinary. Cloudinary – это облачная платформа для управления изображениями и видео, предлагающая их хранение, обработку (трансформацию) и быструю доставку через CDN​
junkevin.medium.com
. Приложение загружает пользовательские фотографии чудес на Cloudinary, получая обратно URL (или уникальный ID), который сохраняется в базе. При отображении изображения в приложении фронтенд получает URL из API и загружает картинку напрямую из Cloudinary CDN, разгружая тем самым наш сервер. Преимущества такого подхода:
Снижение нагрузки на бэкенд: Файлы не проходят через нашу БД, а хранятся на специализированном сервисе, оптимизированном для медиа.
Оптимизация и трансформация: Cloudinary может автоматически сжимать изображения, создавать эскизы, преобразовывать формат, генерировать разные размеры (например, уменьшенные превью) по запросу. Это улучшает производительность загрузки страницы.
CDN: Благодаря CDN у Cloudinary, пользователи по всему миру будут загружать изображения с серверов, близких географически к ним, что ускоряет вывод медиа.
Взаимодействие реализовано через Cloudinary API/SDK на бэкенде: при получении запроса на добавление нового чуда с фото – Spring Boot-контроллер принимает файл (например, multipart/form-data), вызывает Cloudinary API (с ключами авторизации) для загрузки. При успехе Cloudinary возвращает JSON с данными файла (публичный URL, public_id, размеры и пр.). Бэкенд сохраняет ключевые данные (например, URL или public_id) в таблице медиа, связав с соответствующей записью чуда. При запросах чтения бэкенд просто отдаёт сохраненные URL картинок, которые фронтенд использует в <img> или просмотрщике 360°.
Взаимодействие компонентов
Все части системы связаны через четко определенные интерфейсы:
Фронтенд ←→ Бэкенд: общение происходит по REST API через HTTP. Фронтенд отправляет запросы (используя Axios) на адреса бэкенда (например, https://api.example.com/login, .../wonders, .../user-wonders и т.д.). Бэкенд обрабатывает запросы и возвращает ответы с данными в формате JSON. Для защищенных запросов фронтенд включает токен авторизации (JWT) в заголовок Authorization или cookie.
Бэкенд ←→ База данных: внутри сервера Spring Boot использует JDBC (через Hibernate/JPA) для выполнения SQL запросов к PostgreSQL. Например, при GET запросе списка чудес контроллер вызывает метод сервиса, тот – метод репозитория findAll() для сущности Wonder, который под капотом выполнит SELECT * FROM wonders ....
Бэкенд ←→ Cloudinary: при операциях с медиа сервер обращается к Cloudinary API. Для загрузки изображения – отправляется HTTP-запрос (с использованием например Cloudinary Java SDK) с файлом или ссылкой; для удаления – запрос на удаление по public_id. Эти операции обычно выполняются в рамках обработки пользовательского запроса (например, пользователь добавил чудо с фото – бэкенд одновременно создает запись в БД и загружает фото в Cloudinary).
Последовательность при отображении главной страницы:
Пользователь открывает веб-приложение. Фронтенд загружает бандл React и необходимые скрипты.
При инициализации главного компонента, приложение делает запрос GET /wonders к API, чтобы получить список официальных 7 чудес (названия, координаты, возможно краткое описание).
Бэкенд возвращает JSON массив из 7 объектов. Фронтенд отображает глобус и расставляет маркеры в соответствующих координатах.
Пользователь кликает, например, на маркер «Тадж-Махал». Фронтенд выполняет GET /wonders/42 (если ID Тадж-Махала 42) для получения полной информации.
Бэкенд по ID выбирает запись из таблицы wonders, а также связанные записи (например, фотографии из таблицы media, любопытные факты из таблицы facts если есть). Возвращает JSON с полями: название, описание, список фактов, список URL изображений и пр.
Фронтенд получает эти данные и отображает в удобном виде (например, модальное окно или боковая карточка).
Если пользователь не авторизован, на этом этапе он может только просматривать официальные чудеса. Если он логинится (POST /login), то после этого ему становится доступна функциональность добавления.
Авторизованный пользователь кликает «Добавить свое чудо», заполняет форму. При сабмите фронтенд делает запрос POST /user-wonders с JSON данными чуда (название, описание, координаты) и, возможно, отправляет файл изображения через POST /user-wonders/{id}/media или вместе (см. API ниже).
Бэкенд проверяет токен (пользователь авторизован?), затем валидирует данные. Создает новую запись в таблице user_wonders со статусом «PENDING». Возвращает успех.
Теперь, в зависимости от политики модерации, чудо либо сразу становится видимым на карте в слое «пользовательские» (но помечено как не подтвержденное), либо пока не отображается для других. Пользователь может видеть у себя отметку (например, другим цветом) с пометкой «ожидает модерации».
Модератор (роль ADMIN) в админ-интерфейсе просматривает очередь на модерацию (GET /user-wonders?status=pending). Решает одобрить запись и вызывает, например, PUT /user-wonders/105/approve. Бэкенд меняет статус этого чуда на «APPROVED». Теперь оно появляется всем пользователям на карте (в слое пользовательских).
Другие пользователи могут увидеть это пользовательское чудо, прочитать описание, просмотреть фото (которое хранится в Cloudinary – фронт получает ссылку и отображает изображение). Они могут, например, поставить «лайк» этому чуду или поделиться ссылкой в соцсетях (дополнительные функции).

Основные REST API эндпоинты
Ниже приведены основные REST API интерфейсы (URL и действия), обеспечивающие функциональность. Бэкенд следует принципам RESTful: использование методов GET (получение данных), POST (создание), PUT/PATCH (обновление), DELETE (удаление) и четкая структура ресурсов. Аутентификация и пользователи:
POST /register – регистрация нового пользователя. Принимает данные нового аккаунта (логин, email, пароль), создает запись в таблице users. Можно предусмотреть email-подтверждение при регистрации.
POST /login – вход пользователя. Принимает логин/пароль, проверяет учетные данные. При успехе возвращает токен (JWT) и/или устанавливает cookie с сессией. Этот токен должен использоваться в дальнейших запросах для аутентификации.
POST /logout – (опционально, если используется серверая сессия или для явного отзыва токена). Завершает сессию пользователя.
GET /users/me – получить информацию о текущем залогиненном пользователе (например, профиль, достижения, настройки). Требует авторизации.
Официальные чудеса (7 Wonders):
GET /wonders – получить список официальных 7 чудес света. Возвращает массив объектов с основными полями (id, название, координаты, краткое описание, миниатюра изображения). Этот эндпоинт используется для отображения меток на глобусе.
GET /wonders/{id} – подробная информация об одном чуде (по ID). Включает полное описание, исторические факты, развернутый текст, список связанных изображений (URL фотографий, хранящихся на Cloudinary), возможно ссылки на источники.
Примечание: Официальные чудеса редактируются только администраторами, поэтому эндпоинтов POST/PUT для wonders обычно нет для рядовых пользователей. Админ-интерфейс мог бы использовать, например, POST /wonders (добавить новое официальное чудо) или PUT /wonders/{id} (обновить), но эти операции защищены ролью ADMIN.
Пользовательские чудеса (User Wonders):
GET /user-wonders – получить список одобренных пользовательских чудес. По умолчанию возвращает только записи со статусом "APPROVED" (т.е. прошедшие модерацию), чтобы показывать их остальным пользователям. Поддерживает параметры для фильтрации/поиска:
?author={userId} – фильтр по конкретному пользователю-автору (например, вывести все чудеса, добавленные определенным пользователем).
?q={keyword} – поиск по названию/описанию (бэкенд выполнит поиск по подстроке в полях).
?near={lat,lon}&radius={r} – гео-поиск: найти чудеса в радиусе r (км) от точки (lat, lon). Реализуется SQL-запросом с функцией PostGIS ST_DWithin.
GET /user-wonders/{id} – получить детали конкретного пользовательского чуда (если оно опубликовано или если запрос от автора/модератора). Структура ответа похожа на GET /wonders/{id}: содержит название, описание, координаты, ссылки на фото, а также, возможно, информацию об авторе.
POST /user-wonders – создать новое чудо (пользовательский контент). Принимает JSON с необходимыми данными: название, описание, координаты (широта/долгота). Требует авторизации (роль USER или выше). Бэкенд сохраняет запись в БД со статусом "PENDING" (на модерации) и привязывает к текущему пользователю-автору. Вернет созданный объект (в ответе может быть присвоенный id, статус).
POST /user-wonders/{id}/media – загрузка медиа (фото) для созданного чуда. Возможно несколько фотографий – этот эндпоинт можно вызывать несколько раз или позволять загрузку нескольких файлов за раз (например, multipart-запрос с несколькими файлами). Бэкенд сохранит файлы через Cloudinary и привяжет к чуду в таблице media. Альтернативный подход: разрешить отправлять медиа сразу в POST /user-wonders (например, как multipart с JSON и файлом), но разделение на два шага упрощает логику и позволяет сначала создать запись, затем загружать картинки.
PUT /user-wonders/{id} – редактировать своё чудо (название/описание). Разрешено только автору (и модератору/админу). Если запись уже одобрена, редактирование может снова пометить её как требующую проверки или создать новую версию для модерации.
DELETE /user-wonders/{id} – удалить добавленное пользователем чудо. Разрешено автору (до публикации) или администратору/модератору (для уже опубликованных, либо в случае нарушения правил). Удаление должно затрагивать связанные медиа (удалить изображения из Cloudinary) и, возможно, логи (пометить как удалённое, чтобы не нарушить целостность данных, или физически удалить).
Модерация контента:
GET /user-wonders?status=pending – (только для модератора/админа) получить список чудес, ожидающих модерации. Модераторы просматривают эти записи, проверяют описание и фото на соответствие правилам.
PUT /user-wonders/{id}/approve – (только модератор) одобрить пользовательское чудо. Эта операция устанавливает статус записи "APPROVED" и делает её видимой для всех. Может также отправлять уведомление автору об успешной публикации.
PUT /user-wonders/{id}/reject – (модератор) отклонить чудо. Устанавливает статус "REJECTED" (можно удалить или сохранить для истории). Опционально, модератор может прикрепить причину отказа (например, неприемлемое содержимое) – тогда автор увидит, почему отклонено. Отклоненный контент не отображается остальным пользователям.
POST /user-wonders/{id}/flag – (авторизованные пользователи) пожаловаться на неприемлемый контент. Любой пользователь, заметив неподходящее пользовательское чудо, может отправить «флаг». Запрос содержит, возможно, причину жалобы. Бэкенд создает запись в таблице жалоб/флагов. Reactive moderation: приложение позволяет сообществу помечать контент, нарушающий правила​
concentrix.com
 – эти отметки отправляются модераторам.
GET /flags – (модератор) получить список всех жалоб/флагов на контент, не рассмотренных до сих пор. Модератор может перейти к соответствующим записям, при необходимости изменить их статус (например, снять с публикации чудо, если после проверки жалоба обоснованна).
Лайки и отзывы:
POST /wonders/{id}/like – поставить «лайк» официальному чуду.
POST /user-wonders/{id}/like – лайкнуть пользовательское чудо. (Аналогично, можно сделать единый эндпоинт POST /likes с указанием типа и id контента.)
DELETE /user-wonders/{id}/like – убрать свой лайк (если захотят отменить).
(Опционально) POST /user-wonders/{id}/comment – оставить комментарий. (В требованиях не указано, но это возможное расширение социальной функциональности.)
Примечания по API: Все URL и структуры – примерные. В реальном проекте могут использоваться версии API (/api/v1/...), иные названия (например, /auth/login), и более сложные параметры. Важна консистентность: официальные и пользовательские чудеса – два ресурса, поэтому разделены на /wonders и /user-wonders. Лайки, комментарии, поиск – как под-ресурсы или отдельные контроллеры.
Структура базы данных
Структура БД спроектирована для поддержки упомянутых функций. Ниже перечислены основные таблицы и их поля (с указанием важнейших атрибутов):
users – хранит учетные записи пользователей.
id (PK, serial) – уникальный идентификатор пользователя.
username (varchar, unique) – логин.
email (varchar, unique) – email пользователя.
password_hash (varchar) – хэш пароля (пароли не хранятся в открытом виде).
role (varchar) – роль пользователя: например, 'USER' (обычный), 'MODERATOR' или 'ADMIN'. Определяет права доступа (модерацию осуществляют MODERATOR/ADMIN).
created_at (timestamp) – дата регистрации.
... (дополнительно: например, аватар, информация профиля – по необходимости).
wonders – официальные 7 чудес света (наполнение этой таблицы может быть статичным или через админ-панель).
id (PK) – уникальный ID.
name (varchar) – название чудa (например, "Тадж-Махал").
description (text) – описание, история и факты.
location (geometry(Point, 4326)) – географические координаты (точка с широтой/долготой в проекции WGS84). Имеет GIST-индекс для гео-запросов.
country (varchar) – страна или регион (может использоваться для фильтра).
added_by – можно хранить null (добавлено системно) или ID пользователя-админа, который внес запись.
... (при необходимости: год создания, текущий статус – существуют/разрушены, категория и т.п.).
user_wonders – чудеса, добавленные пользователями.
id (PK) – уникальный ID пользовательского чуда.
user_id (FK -> users.id) – ссылка на автора (владелец записи).
name (varchar) – название достопримечательности, придуманное пользователем.
description (text) – описание/история от пользователя.
location (geometry(Point, 4326)) – координаты местоположения. Также индексируется гео-индексом.
status (varchar) – статус модерации: например, 'PENDING', 'APPROVED', 'REJECTED'. По умолчанию при создании = PENDING. Одобренные отображаются всем, отклоненные не отображаются.
created_at (timestamp) – дата добавления.
approved_at (timestamp) – дата одобрения (если есть) и, возможно, approved_by (FK -> users, модератор).
like_count (int) – поле для количества лайков (можно динамически вычислять по таблице likes, но поддерживать счетчик быстрее).
... (возможно, другие метаданные: например, views_count для счетчика просмотров, если нужно, или tags и т.д.).
media – таблица медиа-файлов (изображения, видео) для чудес.
id (PK) – уникальный идентификатор медиа-записи.
wonder_id (FK -> wonders.id, nullable) – если медиа привязано к официальному чуду.
user_wonder_id (FK -> user_wonders.id, nullable) – если медиа для пользовательского чуда.
url (varchar) – URL файла в Cloudinary (или CDN). Может быть также храниться Cloudinary public_id для управления.
type (varchar) – тип медиа: например, 'IMAGE', 'PANORAMA' (для 360° фото), 'VIDEO'. Это позволит фронтенду выбирать способ отображения (панорамные фото — особым viewer, видео — через плеер).
uploaded_at (timestamp).
(Примечание: Можно вместо двух FK использовать одну колонку content_type + content_id, чтобы связать медиа либо с wonders, либо с user_wonders. Но для простоты разделено двумя полями, из которых одно всегда NULL.)
likes – хранит информацию о «лайках» (избранном) от пользователей.
user_id (FK -> users.id) – кто поставил лайк.
wonder_id (FK -> wonders.id, nullable) – какой записи (официальному чуду) поставлен лайк.
user_wonder_id (FK -> user_wonders.id, nullable) – либо какому пользовательскому чуду.
liked_at (timestamp).
(Первичный ключ можно составной (user_id + wonder_id) или (user_id + user_wonder_id) в зависимости от типа, чтобы один пользователь не мог лайкнуть одно и то же дважды. Также возможно разделить на две таблицы: likes_wonders и likes_user_wonders для простоты, но в одном объединенном виде меньше дубляжа кода.)
flags – жалобы/флаги на контент.
id (PK).
user_wonder_id (FK -> user_wonders.id) – ссылка на жалобный контент (предполагается, что жалуются на пользовательские чудеса; при желании можно и на комментарии и пр.).
reported_by (FK -> users.id) – кто пожаловался.
reason (varchar) – причина (можно ограничить набором: «Спам», «Оскорбление», «Недостоверно» и т.п., либо свободный текст).
created_at (timestamp) – когда отправлен флаг.
status (varchar) – состояние жалобы: «NEW» (новая, не рассмотрена), «RESOLVED» (решена).
resolved_by (FK -> users.id) – модератор, который рассмотрел (если решена).
resolution (varchar) – результат: например, «Удалено», «Отклонена жалоба» и т.п.
(Эта таблица помогает модераторам отслеживать пост-модерацию. Можно также в user_wonders иметь счетчик flags_count.)
achievements – (опционально) справочник возможных достижений для геймификации.
id, name, description, criteria (условие получения, например «добавить 5 чудес»).
user_achievements – (опц.) связи пользователей и полученных достижений.
user_id, achievement_id, earned_at.
Связи в целом:
Один пользователь (users) может иметь много пользовательских чудес (user_wonders) – связь 1 ко многим.
Одно чудо (в обеих таблицах) может иметь много связанных медиа (media) – связь 1 ко многим.
Одно чудо может иметь много лайков (likes) от разных пользователей; один пользователь может лайкнуть много чудес – связь многие ко многим реализована через таблицу likes.
Одно пользовательское чудо может иметь много жалоб (flags); одна жалоба связана с одним чудом и одним пользователем (автором жалобы).
Для ролей можно не вводить отдельную таблицу, хранить роль как поле, либо сделать таблицу roles и user_roles для поддержки нескольких ролей у пользователя, но здесь достаточно одной основной роли.
Эта структура БД обеспечивает хранение и быстрый доступ ко всем необходимым данным. Использование PostGIS для координат позволяет эффективно реализовать географические функции приложения. Все текстовые поля (описания, названия) могут быть полнотекстово проиндексированы для удобного поиска, но на небольших объемах можно и простым ILIKE обойтись.
Библиотеки для интерактивного 3D-глобуса
Ключевая визуальная часть проекта – 3D модель Земли с отметками чудес. Реализовать интерактивный глобус в вебе можно разными способами. Рассмотрим рекомендованные решения:
CesiumJS: мощная открытая JavaScript-библиотека для отображения глобусов и 3D-карт прямо в браузере​
cesium.com
. CesiumJS обеспечивает высокую производительность, точность и красивую графику при визуализации Земли. С ее помощью можно добавлять на глобус маркеры по координатам, всплывающие описания, прокручивать/приближать планету, использовать реальные снимки Земли. Для интеграции с React существуют готовые обертки – например, библиотека Resium (React-компоненты для Cesium), позволяющая декларативно описывать 3D-сцену как часть JSX. CesiumJS подойдет, если требуется максимальная реалистичность (он поддерживает 3D-модели, слои рельефа, тайловые карты и пр.). В нашем проекте Cesium позволит отобразить Землю и пометить 7 точек, при клике – управлять камерой (приближать к точке) и отображать всплывающие HTML-аннотации с информацией о чуде.
Three.js + React (react-globe.gl): Более легковесный подход – использовать библиотеку Three.js (для WebGL-3D графики) и готовый React-компонент react-globe.gl. Эта библиотека предоставляет удобный React-компонент Globe, который сразу отображает интерактивный шар (земной глобус) и позволяет наносить маркировки, линии, всплывающие подсказки. React Globe.gl – это React-привязка к движку Globe.gl, использующему Three.js/WebGL​
github.com
. Он хорошо подходит для визуализации именно точек/меток и связанных данных на поверхности земного шара. Например, react-globe.gl позволяет задавать массив точек с координатами и отображать их как маркеры или всплывающие HTML-элементы. Также есть возможность кастомизировать текстуры глобуса (можно добавить изображение земли, облака, звёздный фон и т.п.). Преимущество – простота: несколькими строками мы создаем компонент <Globe /> и передаем ему данные чудес.
Другие варианты: В экосистеме React существуют и другие библиотеки для карт и глобусов. Например, Deck.gl (от Uber) поддерживает режим Globe в комбинации с Mapbox, react-three-fiber – низкоуровневый подход к интеграции Three.js в React. Однако для нашей задачи (только 7 основных точек + пользовательские точки) хватит высокоуровневых решений вроде Cesium или react-globe.gl. Можно даже использовать 2D-карту (например, Leaflet, Mapbox GL JS) в режиме «сплюснутого» глобуса, но 3D-вид делает проект более эффектным.
Выбор: Если проекту важна визуальная реалистичность и потенциал дальнейшего усложнения (например, добавление моделей или прокладывание маршрутов), можно выбрать CesiumJS. Если нужен быстрый результат и достаточный функционал, react-globe.gl будет проще в реализации. Оба варианта могут покрыть требования: показывать маркеры чудес по координатам, реагировать на клики и взаимодействия. Например, CesiumJS поддерживает всплывающие описания через Entity API или custom info boxes, а react-globe.gl может использовать простой callback onClick для маркера, чтобы в React показать свою панель с деталями.
Модерация пользовательского контента
Поскольку пользователи могут добавлять собственные «чудеса», важно реализовать модерацию, чтобы отображаемый контент соответствовал правилам и теме. В архитектуре предусмотрены следующие механизмы модерации:
Ролевая модель: У каждого пользователя есть роль (см. поле role в таблице users). Обычные пользователи имеют роль USER, модераторы/администраторы – MODERATOR или ADMIN. Только модераторские роли могут одобрять или отклонять контент. Роли применяются и на уровне интерфейса (например, модератору доступен раздел «Модерация») и на уровне API (эндпоинты одобрения/удаления защищены).
Премодерация новых чудес: Новые добавленные пользователем точки изначально получают статус "PENDING" (на проверке) и не отображаются всем пользователям на карте, пока их не проверит модератор. Эти записи доступны самому автору (возможно, помечены как "ожидает модерации") и модераторам (в списке на утверждение). Модератор проверяет содержание: убедиться, что это реальное место, соответствующее тематике (достопримечательность, «чудо»), информация не оскорбительна, фото приемлемо (нет запрещенного контента). После проверки модератор либо одобряет (меняет статус на APPROVED) – тогда запись становится общедоступной, либо отклоняет (статус REJECTED) – тогда она остается скрытой. В случае отклонения можно реализовать уведомление автора о причине (например, «не соответствует теме сайта»). Предусмотрена административная UI для модераторов: список всех записей со статусом Pending, с удобной кнопкой Approve/Reject рядом с каждой, а также возможность просматривать подробности (описание, фото).
Постмодерация и жалобы: Даже после публикации, контент может быть пересмотрен. Любой пользователь, обнаруживший проблему (например, фейковая информация или неуместное изображение), может отправить жалобу (флаг)​
concentrix.com
. Как описано, фронтенд предоставляет кнопку «Пожаловаться» на странице пользовательского чуда. При нажатии пользователь выбирает причину и подтверждает. Бэкенд создает запись в таблице flags. Модераторам доступен список новых флагов: они рассматривают каждую жалобу. Если жалоба обоснована – модератор может снять контент с публикации (например, поменять статус обратно на PENDING или полностью удалить). Если необоснованна – пометить жалобу как отклоненную. Этот процесс обеспечивает реактивную модерацию (reactive moderation), полагающуюся на сообщество для обнаружения нарушений.
Интерфейс модерации: Для удобства модераторов можно реализовать отдельную панель (внутри фронтенда, видимую только ролям MODERATOR/ADMIN). Там будут вкладки: «Ожидают одобрения» – список PENDING записей; «Жалобы» – список флагов от пользователей. Модератор может фильтровать по дате, по пользователю. При большом количестве контента такая панель облегчает работу. Также можно настроить уведомления – например, отправлять email администраторам при каждой новой пользовательской добавленной точке или пачке точек за день.
Автоматизированные проверки: В перспективе, можно добавить некоторые автоматические модерации: например, проверять изображения на неприемлемое содержимое через API Cloudinary (у Cloudinary есть addon для автоматического модерации изображений), либо проверять текст на запрещенные слова. Но базово, человеческая модерация (crowd-sourced + admin) достаточно.
Audit Log: Желательно сохранять действия модераторов (кто и когда одобрил или удалил), чтобы иметь аудит истории. Это можно хранить в полях approved_by, approved_at в user_wonders, а также сохранять удаленные записи или причины отклонения.
Сочетая премодерацию и систему жалоб, проект будет поддерживать качество контента: все новые точки проходят проверку перед показом, а уже опубликованные могут быть сняты, если сообщество найдет проблемы.
Дополнительные функции и расширения
Наряду с основными требованиями, можно внедрить дополнительные возможности, делающие проект более интересным и интерактивным:
Система лайков и рейтинга: Позволяет пользователям отмечать понравившиеся чудеса. Реализовано через таблицу likes, как описано выше. На фронтенде – иконка «❤» или «👍» рядом с описанием, показывающая текущий счетчик. Пользователь может кликнуть, чтобы поставить лайк (если авторизован). Можно также ввести рейтинг пользовательских чудес – например, сортировать их по числу лайков, выделять «самые популярные народные чудеса». Это стимулирует качественный контент: авторы будут стараться получить больше лайков. Бэкенд для эффективности может хранить поле like_count и обновлять его транзакцией при новых лайках.
Комментарии и обсуждения: Каждый чудо-объект (особенно пользовательский) мог бы иметь раздел комментариев, где пользователи обсуждают или дополняют информацию. Это увеличит вовлеченность. Комментарии хранятся в отдельной таблице (например, comments с полями id, user_id, wonder_id или user_wonder_id, текст, timestamp). Требуется также модерация комментариев (флаги на них, фильтрация нецензурного текста и т.д.). Эта функция не указана прямо, но логично вытекает из социальной составляющей.
Достижения и геймификация: Внедрение ачивок (badges) сделает использование приложения более азартным. Примеры достижений:
«Первое чудо»: пользователь получает бейдж за добавление первого собственного чуда.
«Исследователь»: за 5 добавленных чудес.
«Популярный автор»: если суммарно его записи набрали 100 лайков.
«Знаток чудес света»: если пользователь просмотрел (кликнул/открыл) все 7 официальных чудес.
«Модератор-ветеран»: для админов, одобривших N записей.
Реализация: предусмотреть определение условий и выдачу наград. Например, при определенных событиях (после добавления чуда, после лайка) проверять, не выполнены ли критерии какого-либо достижения, и если да – записывать в таблицу user_achievements. Фронтенд может показывать значки в профиле пользователя. Это поощряет активность и повторные визиты.
Шеринг (обмен) в соцсетях: Для расширения аудитории и удобства пользователей можно встроить кнопки «Поделиться» – чтобы пользователь мог одним кликом отправить ссылку на чудо в Facebook, Twitter, ВКонтакте и др. При этом желательно сгенерировать open graph данные, чтобы при шаринге красиво отображалось изображение чудa и краткое описание. Это требует на бэкенде либо динамических мета-тегов (если SEO важно) или использование возможностей фронтенда (Navigator.share API для мобильных, или просто копирование ссылки). Каждый чудо (официальный или пользовательский) имеет уникальный URL (например, /wonders/42 или /user-wonders/105), который можно открыть напрямую – фронтенд должен уметь по URL отобразить соответствующую информацию (за это отвечает роутинг React, например React Router).
Поддержка 360° фото и VR: Упомянутая возможность загрузки 360-фото делает проект особенно привлекательным для визуального контента. Пользователь может, например, загрузить панорамный снимок (JPEG с размерами 2:1, equirectangular projection) своего «чуда». Для отображения таких фото фронтенду понадобится специальный viewer: например, библиотека PhotoSphereViewer (есть React-обертки, например react-photo-sphere-viewer) или использование <canvas> + Three.js для текстурирования сферы. При просмотре чудa, если прикреплено панорама-изображение, интерфейс может показать кнопку «Просмотреть в 360°». При нажатии – раскрывается панорамный просмотр, где пользователь может мышкой вращать камеру и осматриваться. Это добавляет эффект погружения. Также, если использовать WebXR API, можно позволить надеть VR-гарнитуру и смотреть панораму в виртуальной реальности. Cloudinary, кстати, поддерживает хранение панорам так же, как обычных изображений (может даже детектировать 360 и выдавать неподвижное превью). Реализация 360-вьюера – фронтенд-задача (JS library), на бэкенде особой разницы нет, просто тип media PANORAMA.
Поиск по карте и маршруты: Дополнительная гео-функция – поиск чудес поблизости или прокладка маршрутов. Например, пользователь разрешает определить свою геопозицию (через браузер Geolocation API), фронтенд отправляет координаты на GET /user-wonders?near=...,radius=... и подсвечивает ближайшие отметки. Или возможность построить маршрут от текущего местоположения до выбранного чуда (можно интегрировать с внешним API, напр. Mapbox Directions, хотя для простоты можно просто открыть ссылку в Google Maps).
Расширение списка официальных чудес: Проект может покрывать не только 7 чудес света (античные или новые), но и другие известные достопримечательности. Можно заранее наполнить базу, или позволить пользователям предлагать «претендентов» на официальные (которые админ может повысить до статуса официального списка). Это уже продуктовые решения.
Мультиязычность: Аудитория может быть интернациональной – стоит предусмотреть локализацию. Хранить описания чудес сразу на нескольких языках (например, таблица wonders_locale с переводами), фронтенд – с поддержкой i18n библиотек (react-i18next). Это расширит охват.
Монетизация (если актуально): Добавление ненавязчивой рекламы туристических услуг, или партнерских ссылок (например, «купить тур к этому чуду света») – как вариант развития, хотя не по технической части.
В рамках технической реализации, все эти фичи опираются на изначально спроектированную архитектуру: мощный фронтенд, API, гео-БД, хранилище медиа. Благодаря модульности React, можно добавлять новые компоненты (комментарии, панорамы) без изменения основ. Бэкенд на Spring Boot легко расширять новыми контроллерами (например, для комментариев, достижений). БД PostgreSQL – добавлением новых таблиц/связей.
